    **Per D-09: Enrich ODataValidationError:**
    - Add `public readonly availableProperties?: string[]` to constructor
    - Update message construction: when availableProperties is provided, append
      `. Available properties: ${availableProperties.join(', ')}` to the message
    - Example output: `"Property 'prce' not found on entity 'Product'. Available properties: id, name, description, price, active, createdAt, updatedAt"`

    **Update ODataQueryPipe to pass available properties:**
    - In `validateFilterNode` PropertyAccess case: collect `knownNames` (already computed) and pass

    - In `validateSelectItem`: same — pass knownNames as availableProperties
    - In `validateExpandNode`: pass navNames as availableProperties
    - Message format per D-09: `"Property '{name}' not found on entity '{entity}'. Available properties: {comma-separated list}"`

    **Per D-10: Enrich ODataParseError with query context:**
    - Add `public readonly queryContext?: string` to ODataParseError constructor
    - Add a static helper `ODataParseError.withContext(message, position, queryString, token?)` that:
      - Extracts ~20 chars before and after the error position from queryString
      - Formats as: `"{message} at position {position}: ...{context}..."`
      - Stores the context snippet in queryContext property
    - Update parser/lexer throw sites to use `ODataParseError.withContext()` when the full query
      string is available. If query string is not easily accessible at the throw site, just ensure
      the position is always set (it already is).

    **Per D-10: Update ODataExceptionFilter:**
    - When catching ODataParseError, include the queryContext in the error response if available
    - Add queryContext to the error details array: `details: [{ target: queryContext }]`
    - This gives API consumers programmatic access to the context snippet

    **Per D-11: No fuzzy matching** — Do NOT add Levenshtein distance, "did you mean", or any
    suggestion logic. Keep error messages clean and deterministic.
